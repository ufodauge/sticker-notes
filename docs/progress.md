## 瓶モード

**3D 版(2026-11-25)**: `src/ui/jar3d/`(`scene3d.ts` 描画、`engine3d.ts` 物理と操作)と `src/core/jar3d.ts`(瓶の断面、カメラ、衝突部品)。three.js(WebGL2)と rapier3d(WASM)。机の円盤、スポットライトと影、旋盤で作ったガラスの瓶、輪郭を押し出したアクリルブロック(輪郭の凸分解を厚みのある凸包にして物理に使う)。瓶は押さないと固定(滑らかなメッシュ)、掴むと動的(凸の壁 141 枚)になり、落ち着いたら固定に戻る。山は全員がほぼ静止したら眠らせる(ぶるぶるしないため)。WebGL2 がなければ従来の 2D 版。残り: 実機の負荷(スマホで 40〜120 枚)、3D 版の見た目の作り込み(瓶の屈折、動的な影、ガラスの映り込み)、カメラの回転と傾き、机の外へ出したブロックの扱い。E2E の 3D の確認は Chromium のソフトウェア WebGL だけ(WebKit は 2D になる)。

- 切り替えと中身の選択は設定(`view`、`jar`)に保存し、起動時に描画の前に読む(Suspense の `use`)ので、保存した表示が最初の描画から出る。`jar` は `{ kind: "auto", seed }` または `{ kind: "manual", ids }`(valibot、`core/jar-selection.ts`)
- 中身は純粋関数 `pickJarIds`: ランダムは種と ID だけで決まる順位の上位 40 枚(`JAR_DEFAULT_COUNT`)、固定は選んだ順の最大 120 枚(`JAR_MAX_COUNT`)。削除したステッカーは、固定では黙って外れる(保存した ID は書き換えない。元に戻せば瓶にも戻る)。新しいステッカーを強制的に入れることはしない(固定では入らない。ランダムでは他と同じ抽選の対象で、40 枚以下なら全部入る)。ランダムでは順位が各ステッカーごとに独立なので、1 枚の増減で瓶が変わるのは高々 1 ブロック
- 瓶のコードは別チャンク(matter-js を含む)。シール帳の表示中は読み込まれない(E2E で確認。オフライン用にサービスワーカーは先に取得する)
- 品質の段階(`core/jar-quality.ts`): 0 = 60Hz・dpr 上限 2、1 = 30Hz、2 = さらに dpr 1、3 = さらに動かすブロックを 160 部品(下記)までにして残りは静止した山。1 フレームの仕事量の移動平均が 10ms を超えたら 1 段下げ、3ms 未満が 240 フレーム続いたら 1 段戻す(戻した直後にまた下がったら待ち時間を倍に)。非表示のフレームは数えない
- 形と見た目(`core/jar-shape.ts`、`core/jar-geometry.ts`、`core/jar-feel.ts`、`ui/jar/glass.ts`、`ui/jar/sprite.ts`): ブロックの輪郭はステッカーの白い土台(余白 4 マス)の外周を `traceContours` でたどり、ドット階段を Douglas-Peucker でならして描く。物理は同じ輪郭を物理用に少し粗くならし、耳切りの三角分割 + Hertel-Mehlhorn の併合で凸な部品に分ける(部品は最大 6 個。超えたら ε を上げて再試行し、最後は凸包。凸包との面積比が 1.08 以下なら最初から凸包)。外部の分解ライブラリ(poly-decomp)は入れず、純粋関数として `src/core` に置いて決定的にテストできるようにした。複数の塊は凸包でつなぎ、穴は白い土台が埋めるので輪郭は 1 本。全部透明・小さすぎるものは小さな丸い四角。大きさは「ステッカーの辺」を 1 とした単位座標なので、形ごとの面積では変わらない
- 瓶のガラスは 2 枚の静的 canvas(ブロックの後ろ: 床の影、空洞の色、奥行き、縁の奥側 / 前: 壁と底の厚み、縁のふちの明るさ、ハイライト、縁の手前側)を、サイズ・解像度の段階が変わったときにだけ描く。毎フレームのコストはゼロ。物理の壁は瓶の内側の輪郭(丸い底の角を含む多角形)に沿った厚い板。ブロックの絵は 1 枚ずつ焼き込み(厚み、屈折して見える絵、内側の光、斜めの反射、影)。壁にめり込んだブロックは瓶の口から戻す(`rescueStrays`)
- 振る動き(`core/jar-feel.ts` の `JAR_FEEL` に定数を集約。速度は 1 ステップあたり「ブロックの辺」の倍数): 3 回の弱まるパルス(0 / 150 / 310ms、強さ 1 / 0.7 / 0.45)、上向き 0.1、横 0.05、回転 0.05。どんな力でも速度は 0.16 辺 / ステップまで。反発 0.04(壁 0.02)、空気抵抗 0.022、回転は毎ステップ 0.985 倍、眠るまで 40 ステップ。動いているものがすべて十分に遅い状態が 90 ステップ続いたら全部眠らせる(深い山の微振動で止まらないのを防ぐ)
- 品質の段階の「動かすブロック数の上限」は、部品数(凸な部品の合計)で数えるようになった(段階 3 は 160 部品)。複合ブロックは衝突の組が増えるため
- 計測(Chromium、デスクトップ、段階 0、手作りの形 12 種を混ぜた並び。1 回あたりの仕事量の平均 / 最悪): 40 枚(79 部品)は 0.66 / 1.1ms(変更前 0.33 / 0.5)、120 枚(237 部品)は 1.9 / 2.6ms(変更前 0.89 / 1.9)。重くなったのは複合ブロックの衝突。ガラスは静的 canvas なので描画は増えていない
- 暗い部屋と明かり(`core/jar-light.ts`、`ui/jar/lighting.ts`、`ui/jar/glass.ts`、`ui/jar/Jar.module.css`、`ui/jar/chrome.ts`):
  - 瓶モードはいつもダーク。シール帳はシステムのテーマのまま。切り替えは `<html data-view="jar">` で、瓶を表示している間だけ App のルート要素の ref コールバックが付け外す(切り替えと同じコミットなので、ちらつかない)。index.css の `:root[data-view="jar"]` がダークのトークンと `color-scheme: dark` を持つので、ツールバー、操作バー、トースト、瓶から開いたダイアログ(選ぶ、メニュー、作る、印刷)まで全部がダークになる(トークンは DOM の継承で、ダイアログもシェルの中にあるため)。QR のダイアログだけは従来どおり白のまま。ブラウザの色(`<meta name="theme-color">`)は同じ ref コールバックが先頭に足す
  - 瓶のまま再読み込みしたときの最初のフレーム: 保存した表示は IndexedDB(描画の後に読める)なので、`localStorage` に `view-hint` を写しておき、index.html の小さなスクリプトが描画前に `data-view` を付ける(`data/view-hint.ts`)。ヒントは見た目だけのもので、本当の設定は IndexedDB。ステッカーの読み込み中も瓶ならダークのまま
  - 部屋・明かり・テーブル・光だまり・ほこりは CSS(静的なグラデーションなのでフレームごとのコストなし。円錐は `conic-gradient` とマスク、ほこりは 12 個の transform / opacity のアニメーションで、動きを減らす設定では非表示)。瓶の箱が `container-type: size` で、箱の幅(cqw)を基準に配置する。瓶のガラスの 2 枚の canvas には、口から入る光、床の光だまり、縁の手前側の発光(明かりは真上)、前面の canvas に `-webkit-box-reflect` でテーブルへの映り込みを足した
  - ブロックへの光: 1 フレームにつき、ブロックを描いた後に「光の段階」の絵(`makeGrade`。`lightAt` から作る半解像度の canvas。サイズが変わったときだけ作り直す)を `source-atop` で 1 回重ねる(上は暖かく明るく、下と外側は暗く)。さらに、角度が合ったブロックの輪郭の最も上の点に、小さな星形の光(`makeGlint`、`lighter`)を重ねる。光る強さは角度の関数(回転 1 周に 3 回、鋭い)で、位相はブロックごとに違う。スプライトの絵は毎フレーム描き直さない
- 音(`core/jar-sound.ts` の純粋な対応表と、`ui/jar/sound.ts` の Web Audio。音声ファイルなし):
  - ぶつかり: 相対速度(ブロックの辺 / ステップ)から、相手で 3 種類の音になる(ブロック同士はカチッ = 2〜3 個のずれた三角波 1.3〜3.3kHz + 数 ms のノイズ、ガラスの壁はコン = 400〜700Hz の減衰が長い正弦波、底はドン = 90〜150Hz の正弦波が下がる)。速度 0.03 辺 / ステップ未満は鳴らさず、0.14 で最大。音程はブロックが大きいほど低く、揺らぎ(乱数)で毎回少し違う。振る = パルスごとに細かいティックの束、入ってくる新しいブロック = ぽとん(最初から入っているブロックは鳴らさない)
  - 制限: 同時 12 音まで、種類ごとの最小間隔(カチッ 20ms、コン 30ms、ドン 40ms、ぽとん 60ms)、マスター -12dB + コンプレッサー(リミッター代わり)。ノイズのバッファは 1 つを使い回す。衝突 1 回あたりの仕事は、最も強い組を選ぶだけ
  - 開始と停止: `AudioContext`(なければ `webkitAudioContext`)は、最初の操作(瓶への切り替えのボタン、「振る」、ブロックへのポインタ、スピーカーのボタン)の中で作って `resume()` する(iOS の自動再生の制限。無音の 1 サンプルも鳴らす)。ページが隠れたら `suspend()`、戻ったら `resume()`。瓶を出る、エンジンを止める、スピーカーをオフにすると `close()`。動きを減らす設定では作らない
  - スピーカーのボタン(`aria-pressed`)は振る・傾きと同じ列。設定 `sound`(valibot の boolean)に保存し、既定はオン(ただし最初の操作までは鳴らない)
- 計測(Chromium、デスクトップ、段階 0、手作りの形を混ぜた並び。1 回あたりの仕事量の平均 / 最悪): 40 枚(79 部品)は 0.94 / 2.4ms(暗い部屋にする前 0.76 / 1.6)、120 枚(237 部品)は 1.95 / 3.5ms(前 2.04 / 3.5)。ほぼ同じ(測るたびに ±0.3ms ほどぶれる)。光の絵はブロックのある範囲だけ重ねる。静的な層(部屋、円錐、テーブル、ガラス)は毎フレームのコストなし
- 見た目で残っていること: 形違いのブロックが重なった山は実機で確認していない。絵は焼き込みなので、斜めの反射と厚みの向きはブロックと一緒に回る。120 枚で底の近くが少し重なって見える(既存の弱点)
- テスト用の計測口(`window.__jarProbe`)は、ビルド時に `VITE_JAR_PROBE` を付けたとき(E2E のビルド)だけ入る。通常のビルドには含まれない
- 実測(Playwright、ヘッドレス Chromium、デスクトップ、Pixel 7 エミュレーション。**スマホの数値ではない**)。「振る」を押してから静止するまでの、物理 + 描画の 1 回あたりの平均 / 最悪(ms)と、処理した回数:

| 枚数 | 段階 0 | 段階 1 | 段階 2 | 段階 3 |
| --- | --- | --- | --- | --- |
| 20 | 0.18 / 0.4(246 回) | 0.21 / 0.5(110 回) | 0.22 / 2.2(138 回) | 0.20 / 0.4(139 回) |
| 40(既定) | 0.34 / 0.6(200 回) | 0.35 / 0.6(91 回) | 0.37 / 1.9(96 回) | 0.31 / 0.6(133 回) |
| 100 | 0.70 / 1.4(162 回) | 0.69 / 1.4(103 回) | 0.74 / 1.7(96 回) | 0.68 / 1.0(78 回、20 枚を静止) |
| 300(負荷試験) | 2.20 / 5.7(144 回) | 2.50 / 5.7(83 回) | 2.78 / 5.2(76 回) | 1.32 / 1.9(72 回、220 枚を静止) |

  1 回あたりの仕事量は段階 1 以降も大きくは変わらず、1 秒あたりの回数が半分になる(30Hz)ことで負荷が下がる。段階 3 だけは 1 回あたりも下がる。このヘッドレス環境では dpr の差はほとんど出ない。300 枚は `JAR_PERF=1` の負荷試験で、アプリの通常の使い方(最大 120 枚)の外
- 実機で確認が残るもの: 低価格 Android と iPhone での 40 枚・120 枚の操作感、iOS の傾きの許可の流れ、振動(Android Chrome)、WebKit(iPhone)での性能、暗い部屋の実機での見た目(OLED で黒が沈みすぎないか、明るい屋外で見えるか、映り込みの `-webkit-box-reflect` が Firefox では出ない)
  - 音(耳でまだ聴いていない。数値と配線だけ検証済み): iOS Safari で最初の操作から鳴るか、マナーモード(消音スイッチ)のときの鳴り方(Web Audio は消音スイッチで止まる端末がある)、ホーム画面アプリでの鳴り方、Android Chrome での遅延、実機のスピーカーとイヤホンでの音量(-12dB のヘッドルーム、コンプレッサーの強さ)、鳴らしすぎ・うるさすぎ(公共の場所で意外に鳴らないか。ボタンの位置)、各音の音色(カチッ、コン、ドン、ぽとん、振る音)の好み。調整値は `core/jar-sound.ts` に集まっている

## 網点(ディザ)

- 作成ダイアログに、写真だけで使える「網点でなめらかに」のトグルを足した(初期はオフ、画像を開き直すとオフに戻る。クロップやパレットを変えても保持)
- 手法は Bayer 4x4 の整列ディザ。OKLab で最も近い 2 色の間のどこにあるかを閾値と比べて 2 色から選ぶので、パレット色そのものの平坦な面は平坦なまま、グラデーションは 2 色の比率で再現される(誤差拡散は偏ったパレットで崩れたため不採用)
- パレットの自動順位は網点なしの誤差のまま。ペイロードの形式は変わらず、ドット絵の取り込みと少色画像の 1 対 1 対応には使わない。実機で見た目の好みを確認する

## 規模の目安(e2e/scale.spec.ts、デスクトップ)

ステッカー 300 枚、1 ページに 60 枚を貼った状態。

| 項目 | Chromium | WebKit(Playwright の Windows 版) |
| --- | --- | --- |
| バックアップ読み込み | 約 0.1 秒 | 約 6 秒(ほぼ IndexedDB への 300 件の書き込み) |
| ページ表示 | 約 0.2〜0.3 秒 | 約 0.2 秒 |
| 一覧表示 | 約 0.3〜0.5 秒 | 約 0.3 秒 |
| ドラッグ中の最長フレーム間隔 | 70〜150ms | 約 17ms |

WebKit の読み込みの遅さは Windows 版 WebKit 固有の可能性がある。iPhone の Safari で測って、遅ければ分割書き込みと進捗表示を入れる。

## 実装中に直した不具合

- 保存中に次のステッカーのリンクを開くと、前の保存が新しいリンクの `#` を消していた(回帰テストあり)
- Playwright の WebKit で `createImageBitmap` が画像を読めなかった。`<img>` での読み込みにフォールバックする

## パレット評価

- 自動選択の基準は、3x3 のボックスぼかし(OKLab、端はクランプ、透明画素は平均にも誤差にも入れない)をかけた元画像と量子化結果の二乗誤差の和。1 対 1 対応の少色画像は従来どおり
- 単色系(Grayscale / Sepia / Matcha / Indigo / Crimson)は `kind: "filter"` で、自動選択の対象外。作成ダイアログでは自然なパレットの下に区切って並べ、手動で選べる(ドット絵が完全一致するときは従来どおり選ばれる)
- 個人写真 77 枚: 単色系の自動選択は 66% から 0%、自然なパレット 27 種のうち一度も選ばれないものは 11 種
- `node scripts/palette-eval.ts <写真フォルダ> <出力フォルダ>` で plain / blur3-all / app(アプリと同じ `rankPalettes`)を比べる。写真と出力はコミットしない

## パレットの入れ替え(P6)

- 凍結の方針を変更: 公開(告知)前は中身を変えてよい(AGENTS.md、plan.md、palette-data.ts 冒頭を更新)。公開後は ID ごとに凍結
- 一度も選ばれず、フィルターとしての価値も薄い 9 種(Macintosh II、Neon、Sunset、Candy、Twilight、Rainbow Light、Rainbow Vivid、Night City、Desert)と、近い茶系の Portrait を、自作の 10 種に置き換えた: Skin Tones(10)、Overcast(7)、Mist(12)、Daylight(15)、Clear Sky(16)、Stage Light(20)、Lamplight(21)、Everyday(25)、Snapshot(26)、Night(30)
- 色は学習用の写真(77 枚のうち 52 枚)の OKLab k-means で出し、手で調整(各パレットで最小色間距離 0.03 超、暗色と白に近い色を含む)。写真と派生画像はコミットしていない。いずれも `source: "self"`。M0 の「公開パレットのライセンス確認」の対象は、残った Lospec 由来の 9 種だけになる
