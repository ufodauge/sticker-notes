# ステッカー交換アプリ 実装計画

## 前提

疑問・より良い提案があれば都度確認すること。

## 概要と確定事項

ブラウザだけで、32×32・16色のドット絵ステッカーを交換し、シール帳に集めるアプリを作る。サーバーは置かず、静的ホスティング(GitHub Pagesなど)だけで動かす。近接では QR コードで、SNS上では URL 経由で交換する。

| 項目 | 決定 | 理由・備考 |
| --- | --- | --- |
| 交換手段 | QRコード。相手は標準カメラで読み、URLのフラグメント(#以降)にステッカーを載せる | 音と位置情報は騒がしい屋外で当てにならない。Web NFCはスマホ同士の交換に使えない |
| 双方向の交換 | QRを2回スキャン(A→B、B→A) | サーバーなしでは、1枚のQRで運べるのは表示した側の情報だけ |
| 画像 | 32×32、16色。パレットは32種から1つ選ぶ | パレット選択は5ビットで足りる |
| 透明 | 16色のうち1色を「透明」に指定できる(任意) | 透明にした色は不透明ピクセルには使えない |
| 付加情報 | SNS種別+ID(名前は載せない)。種別はX、Instagram、Bluesky、Discordの4つ | 種別ごとに文字種と長さを検証する |
| 作成方法 | 画像インポート(アプリ内のドット絵エディタは作らない) | 外部ツールで描いた絵もインポートで取り込む |
| 見た目 | 不透明部分を縁取り、囲まれた穴は白地で埋める | 印刷時はこの輪郭をカットラインにする |
| 保存 | 端末内のIndexedDB。バックアップはファイルで書き出す | サーバーがないので、端末の外には何も残らない |
| 印刷 | SVGで出力する | 拡大してもドットがにじまない |
| QRの読み取りにくさ | 密度が高いときだけ軽い警告を出す。作成は止めない | 警告のしきい値は実機で決める |
| ホスティング | GitHub Pagesのドメインのまま使う | 独自ドメインにしてもQRの密度はほとんど変わらない |
| ステッカーの貼り方 | 同じステッカーは1回だけ貼れる | 別ページへは移動で動かす |
| 受け取りの履歴 | 受け取った日付だけを記録する | 場所は記録しない |
| なりすまし | 対応しない | IDの持ち主を確かめる手段がない |
| ライブラリ | 信頼されているOSSを優先して使う | 自作は仕様そのものに関わる部分に絞る(「技術構成とテスト方針」参照) |

スコープ外: アプリ内ピクセルエディタ、サーバーとアカウント、不適切な画像の自動検出、背景除去、音・位置情報・Bluetoothを使った交換、1回のスキャンで両方向を交換する仕組み。

## ペイロード仕様 v1

本文は「2バイトのヘッダ + SNS ID + 512バイトのピクセル」で、圧縮前は 515 + n バイト(n = IDのバイト数、最大は64)。IDが20バイトなら535バイト、最長の64バイトで579バイトになる。

| オフセット | 長さ | 内容 |
| --- | --- | --- |
| 0 | 2バイト | ヘッダ(下表、ビッグエンディアン) |
| 2 | 1バイト | IDの長さ n(1〜64) |
| 3 | nバイト | SNS ID(UTF-8) |
| 3 + n | 512バイト | ピクセル。パレット番号4ビット/px、行優先、上位ニブルが先 |

| ビット | 幅 | 内容 |
| --- | --- | --- |
| 15〜11 | 5 | パレットID(0〜31) |
| 10 | 1 | 透明あり(1 = あり) |
| 9〜6 | 4 | 透明にするパレット番号(0〜15)。透明なしのときは0 |
| 5〜0 | 6 | SNS種別(1 = X、2 = Instagram、3 = Bluesky、4 = Discord。それ以外は拒否) |

版は URL の `#v1.` で区別する。将来ヘッダを変えるときは v2 を切り、v1 の読み取りは残す。

**ステッカーID**: 圧縮前の本文のSHA-256の先頭16バイト(hex 32桁)。圧縮後ではなく圧縮前にする理由: 圧縮実装の違いでバイト列が変わっても、同じステッカーを同じと判定できる。シール帳での重複排除に使う。

**受信時の検証**(どれか1つでも違反したら、一部だけ採用せず全体を拒否する):

- 展開後の長さがちょうど 515 + n バイト。展開サイズに上限(1KB程度)を設け、圧縮を悪用した巨大データを防ぐ
- パレットIDが用意した種類数未満
- SNS種別が1〜4のどれかで、IDが1〜64バイト
- IDが正しいUTF-8で、SNS種別ごとの許可文字(「ステッカーの見た目」の表)だけでできている
- IDに制御文字、ゼロ幅文字、双方向制御文字(表示の左右が入れ替わって見える)を含まない

**テストベクタ**: ステッカー3〜5件(全透明、最長ID、ノイズ、実例など)の「入力 → 本文バイト → URL」をJSONで固定し、実装を変えても出力が変わらないことをCIで確かめる。

## QR・URL設計

URLは `https://<host>/<path>/#v1.<本文>` とし、本文を英数字モード用の43文字で符号化する。base64urlより、QRの一辺が8〜12モジュール(約1バージョン分)小さくなる。

実測(試作スクリプト、誤り訂正M、固定パレット、ID 15文字、プレフィックス `https://example.github.io/s/#v1.`、OpenCVで復号を確認):

| サンプル | 本文(圧縮後) | 方式 | URL文字数 | QRバージョン | 一辺のモジュール数 |
| --- | --- | --- | --- | --- | --- |
| スライムのドット絵 | 163バイト | base64url | 250 | v11 | 61 |
| スライムのドット絵 | 163バイト | 43文字(英数字モード) | 277 | v10 | 57 |
| ノイズ(最悪ケース) | 530バイト | base64url | 739 | v22 | 105 |
| ノイズ(最悪ケース) | 530バイト | 43文字(英数字モード) | 827 | v19 | 93 |

最悪ケースでは、誤り訂正をMからQに上げると、43文字方式では 93 → 109モジュール(v19 → v23)、base64urlでは 105 → 121(v22 → v26)になる。誤り訂正はMを既定にする。Lは小さくなるが、屋外の汚れや傾きに弱い。

**43文字方式の中身**

- 文字は `0-9 A-Z $ * + - . / :` の43種。空白と `%` はURLで壊れるので除く
- 本文2バイトを3文字にする(43の3乗は65536以上)。最後の奇数バイトは2文字
- QRは2セグメントにする。URLの頭(`https://…#v1.`)はバイトモード、本文は英数字モード。複数セグメントに対応したQR生成ライブラリ(NayukiのqrcodegenなTypeScript版など)が必要
- プレフィックスを `https://s.app/#v1.` のように14文字短くしても、上の2サンプルではバージョンが変わらなかった。短縮ドメインは不要
- 圧縮はdeflate(raw)。実装は fflate に一本化する(ブラウザ標準の CompressionStream との二重実装を避ける)

**密度の警告(暫定)**: QRの一辺が73モジュール(v14)以上で「やや細かい」、89モジュール(v18)以上で「細かい」として、「色数や模様を減らすと読み取りやすくなります」というヒントを出す。作成や交換は止めない。上のサンプルでは、ドット絵は警告なし(v10)、ノイズは「細かい」(v19)になる。しきい値は実測で決める: M2の実機テストで、標準カメラが明るい屋外1秒以内に読める距離を測る。

**表示の工夫(屋外向け)**

- 白地に黒、余白(クイックゾーン)は4モジュール。ダークテーマでも反転しない
- モジュール1個をデバイスピクセルの整数倍で描く(canvasで整数スケール)。にじみで読み取り率が落ちるのを防ぐ
- 全画面表示に切り替えられ、Screen Wake Lock で消灯させない(非対応ブラウザでは無視)
- 明るさはWebから上げられないので、「画面の明るさを上げてください」と案内する

実機で確認する点: iPhoneとAndroidの標準カメラが、`$ * +` を含む長いフラグメントのURLを欠落なく開けるか。

## 交換フローと受信

交換は「見せる → 読む」を、お互いに1回ずつ行う。受け取った側は、開いたページで内容を確認してから保存する。

1. 「交換」画面で、自分のステッカーを1枚選ぶ。全画面のQRが出る
2. 相手が標準カメラでQRを読む。ブラウザでアプリが開き、URLの `#v1.…` を受信する
3. 受信画面に、縁取りとSNSラベル付きのプレビュー、「シール帳に追加」と「破棄」を出す
4. 追加すると保存し、`history.replaceState` でURLから `#…` を消す(再読み込みで二重に取り込まない)
5. 役割を入れ替えて、もう1回行う

- 検証に失敗したときは「読み込めないステッカーです」とだけ表示し、理由の詳細は出さない
- ステッカーIDが同じものをすでに持っているときは、追加せず「すでに持っています」と出す

**初回アクセスは通信が要る**: 受け取る人がアプリを使ったことがないと、QRを読んだ瞬間にページを取得する通信が必要になる。人が多い屋外では電波が弱いことがあり、ここが「ブラウザ完結」でも解決できない。対策は次の2つ。

- Service Workerでアプリ一式をキャッシュし、2回目以降は圏外でも開けるようにする
- 事前に開いておいてもらう案内(イベントでの告知や、交換画面の文言)を用意する

**iOSではカメラから開いたSafariとホーム画面アプリで保存先が別になる**(私の知る限りで、実機で要確認)。このままだと、Safariで取り込んだステッカーがホーム画面アプリに見えない。

- 受信画面に「リンクをコピー」を用意し、ホーム画面アプリ側に「貼り付けで取り込む」入力欄を置く
- Safariで開いたときは、ホーム画面への追加を促す案内を出す(保存が消えるリスクにも関係する。「シール帳・保存・バックアップ」を参照)
- AndroidのChromeでインストール済みのWebアプリがあるとき、カメラからのリンクがどちらで開くかは未確認。M2で実機検証する

## ステッカー作成(画像インポート)

ステッカーは画像インポートだけで作る。画像を選び、正方形に切り抜き、32×32に縮小し、パレットを選び、透明とSNS情報を設定する。結果のプレビューは常に横に出し、画像は端末の外に送らない。

1. **画像選択**: ファイル選択(PCはドラッグ&ドロップも)。`createImageBitmap` で読み込み、EXIFの向きを反映する
2. **クロップ**: 1:1の枠をドラッグとピンチで動かす。左に元画像と枠、右に32×32の結果を8倍で表示(最近傍拡大)
3. **縮小**: 既定は面積平均(写真向け)。すでにドット絵の画像向けに「ドット絵モード」(最近傍)を用意する。縮小はブラウザの描画ではなく自前の関数で行い、ブラウザごとの縮小品質の差を避ける。32×32ちょうどの画像はクロップと縮小を飛ばす
4. **パレット**: 32種すべてで量子化して誤差を比べ、最小のものを自動で選ぶ。32個の小さなプレビュー一覧から手動でも切り替えられる
5. **透明**: 元画像のアルファが半分未満のピクセルを透明にする。パレットごとに「透明候補の番号」(既定はそのパレットの最も明るい色)を持ち、利用者は任意の番号に変えられる。透明にした番号は不透明ピクセルには使えないので、不透明側は15色で量子化する
6. **SNSとID**: 種別を選びIDを入力。種別ごとの許可文字と長さで入力中に検証する。「QRを読んだ人全員にIDが渡ります」という注意を表示する
7. **保存**: QRの密度(警告があればそれも)を表示して、「自分のステッカー」として保存する

**量子化の中身**

- 色の距離はOKLabのユークリッド距離の2乗。パレットの16色はあらかじめOKLabに変換して持つ
- 誤差は全ピクセルの最小距離の合計。1,024px × 16色 × 32パレット ≈ 52万回の距離計算で、クロップを動かすたびに再計算できる規模
- ディザは既定でオフ。32×32ではノイズに見えやすいので、後から順序ディザ(Bayer 4×4)を足せる形にしておく
- 判定と変換は純粋な関数(`quantize(rgba, palette, transparentIndex) → {indices, error}`)にし、UIから切り離してテストする

**パレット固定モード(外部ツールで描いた絵向け)**

- 各パレットを 16×1 のPNGと .gpl(GIMP形式)でダウンロードできる。外部のドット絵ツールでそのパレットを使って描けば、誤差0で取り込める
- 画像が32×32で、全ピクセルがあるパレットの色と完全一致するときは、そのパレットを自動で選び、変換せず番号に置き換える

後回し: 背景除去、明るさ・コントラストの補正、取り込み後の1ピクセル修正。

## ステッカーの見た目

ステッカーは「ドット絵 + 縁取り」を1枚の絵として描く。描画は、ペイロードから作る純粋関数で行い、画面・シール帳・印刷で共通に使う。

**縁取りと白地**

1. 不透明ピクセルのマスクを r px 膨張させる(既定 r = 2、実機で調整)
2. 膨張したマスクの外側とつながらない穴(囲まれた空白)を埋めて、シールの白地にする
3. 白地の上にドット絵を重ねる。内側の透明ピクセルは白地として見える

画面上はドット単位の縁取りにして、絵と粗さを揃える。印刷用のカットラインは、この輪郭をなぞって角を丸めたパスにする(「印刷」を参照)。

**SNS種別とリンク(4種に決定)**

許可文字と長さ、URL形式は暂定で、実装前に各サービスの現行ルールを確認する。

| 番号 | 種別 | IDの許可文字(案) | リンク先 |
| --- | --- | --- | --- |
| 1 | X | 英数字と `_`、15文字まで | `https://x.com/{id}` |
| 2 | Instagram | 英数字と `.` `_`、30文字まで | `https://www.instagram.com/{id}/` |
| 3 | Bluesky | ハンドル(`name.bsky.social` のようなドメイン形式、64バイトまで) | `https://bsky.app/profile/{handle}` |
| 4 | Discord | 小文字英数字と `.` `_`、2〜32文字(現行のユーザー名の規則、暫定) | リンクなし |

**リンクの安全対策**(IDは渡された外部入力なので、常に疑う)

- リンクは、検証を通ったIDからテンプレートで組み立てる。IDをそのままURLにしない
- 開くのはタップしたところだけ。行き先のホスト名を確認表示してから、`rel="noopener noreferrer"` で新しいタブに開く
- Discordはリンクにしない

## シール帳・保存・バックアップ

シール帳は「持っているステッカー全部(コレクション)」と「貼るページ」の2層にする。保存は端末内のIndexedDBだけなので、消えうる前提で、永続化の要求とファイルのバックアップを最初から入れる。

| ストア | 主な項目 | 備考 |
| --- | --- | --- |
| stickers | id(ハッシュ)、body(圧縮前の本文)、origin(`mine` / `received`)、receivedAt(日付のみ、YYYY-MM-DD) | 1件約 0.6KB。件数が増えても容量は問題にならない |
| pages | id、order、background | 縦横比は固定(例: 3:4) |
| placements | id、pageId、stickerId、x、y、scale(整数1〜4)、rotation、z | stickerIdを参照する。1ステッカーにつき配置は1つだけ(stickerIdを一意にする) |
| settings | 交換で使う自分のステッカーの既定、バックアップした日 |  |

**配置操作(タッチ中心)**

- ドラッグで移動、ピンチかハンドルで拡大縮小(整数倍にスナップ)と回転、タップで最前面。「はがす」とページから外れるが、コレクションには残る
- 拡大縮小を整数倍にする理由: ドットがにじまない。回転は自由。画面上では斜めのドットがギザギザになるが、雑に貼った風合いとして許容する(印刷はSVGなので回転してもきれい)
- 描画は、事前に描いた絵(canvasまたはImageBitmap)を、`image-rendering: pixelated` で並べる。数百枚規模を想定し、性能はM5で実測する
- ページの背景は単色と簡単な模様を数種類。ページ数に上限は設けない
- コレクション一覧は、新しい順やSNS種別で並べ替え、IDの部分一致で検索できる

**消えるリスクへの対策**

- `navigator.storage.persist()` を要求する。許可されるかはブラウザ次第なので、設定画面に結果を表示する
- iOS Safariは、ホーム画面に追加していないサイトのデータを、一定期間使わないと消すことがあるはず(私の知る限りで、実機で要確認)。ホーム画面への追加を促す
- バックアップ: 「書き出し」で、ステッカー本文(base64)、ページ、配置を1つのJSONファイルにしてダウンロードする。「読み込み」はマージで、同じIDのステッカーは重複させない。形式にはバージョン番号を入れる
- 受け取りが10枚増えるごとに、バックアップを促す表示を出す
- 端末の乗り換えも、この書き出しと読み込みで行う(QRには全部入らない)

## 印刷

印刷はSVGで1枚のA4シートを作り、ブラウザの印刷機能で出す。PNGではなくSVGにする理由は、拡大と印刷でドットがにじまないこと。

- **ドット絵**: 1ドット = 1矩形。横に並ぶ同じ色は1つの矩形に結合して、数を減らす。矩形の縫目が見えないように `shape-rendering="crispEdges"` を使う
- **カットライン**: 縁取りの輪郭をなぞり、角を丸めた細い線を別のグループで描く。ハサミで切る人向けに表示を切り替えられる
- **サイズ**: 1ドットの長さをmmで指定する(既定 1.5mm、絵が48mm角)
- **割り付け**: 選んだステッカーを、A4縦に自動で並べる(余白5mm、間隔3mm)。同じステッカーを複数枚並べることもできる
- **出力**: `window.print()` と `@page { size: A4; margin: 0 }`。PDF保存はブラウザの印刷ダイアログから行う
- **色**: 画面と印刷で色味が変わる(特に鮮やかな色と暗い色)。パレットは画面で決める前提とし、M6で試し刷りして確かめる

## 技術構成とテスト方針

Vite + React + TypeScript の静的サイトとして作り、ロジックの核をブラウザAPIに依存しない純関数に集める。核をNodeでテストできるので、UIを後から変えても仕様がぶれない。

**使うもの(案)**

- ビルド: Vite。GitHub Pagesのサブパス(`/repo/`)で配信する場合は、Viteの `base` とService Workerのスコープを合わせる
- PWA: vite-plugin-pwa(オフライン起動とホーム画面追加)
- 保存: idb(IndexedDBの薄いラッパー)。状態管理は小さいものでよい(jotaiなど)
- 圧縮: fflate。QR: qrcodegen(TypeScript版、複数セグメント対応)。ハッシュ: SubtleCrypto(SHA-256)
- テスト: Vitest(核)、Playwright(画面。WebKitでも回す)、QR復号の検証に jsQR など別実装のデコーダ
- ほか: vite-plus (pnpm), oxc, react compiler, typescript 7.1 beta, css modules (ts7.1 の content mapper で型解決できるように)
  - useEffect は特定のディレクトリでのみ利用を許可し、クリーンアップ関数もなく、副作用を解除しない effect の利用を抑制する厳しい lint rule を作成する
  - let やミュータブルなオブジェクトではなく、readonly なステートマシンの利用を優先する。useState より useReducer の利用を優先する。
  - 必要以上にレイアウトスラッシングの発生がしないよう徹底する

採用方針: 信頼されているOSSを優先し、自作は仕様そのものに関わる部分(payload、43文字符号化、縁取り、量子化の評価)に絞る。採用前に、ライセンス、最終更新日、利用実績を確認する。候補(いずれも未確認): クロップ操作は react-easy-crop、色空間変換は culori。

**モジュール構成**

| モジュール | 役割 | 依存先 |
| --- | --- | --- |
| core/payload | 本文の符号化・復号・検証、ステッカーID | なし(純関数) |
| core/palette | 32種のパレット定義、OKLab変換 | なし |
| core/quantize | 画像 → パレット番号、パレット自動選択 | palette |
| core/render | パレット番号 → RGBA、縁取り、白地、輪郭抽出 | palette |
| core/sns | SNS種別、ID検証、リンク生成 | なし |
| core/qr | URL組み立て、43文字符号化、QR行列、密度判定 | payload、qrcodegen |
| data/db | IndexedDB(stickers、pages、placements)、バックアップ | payload |
| ui/\* | 交換、受信、作成、シール帳、印刷の各画面 | core、data |

守るルールは2つ。core はDOMやブラウザAPIに依存しないこと、パレットIDは一度決めたら中身を変えないこと(色を足すなら新しいIDを振る。変えると過去に交換したステッカーの色が変わる)。

**自動テスト**

- 往復: 任意のピクセルとIDで、符号化して復号した結果が元と一致する。奇数長を含む 43文字方式の往復も確かめる
- テストベクタ: 固定入力 → 固定URL。実装を変えても変わらないこと
- 拒否ケース: 長さ違い、不正文字、双方向制御文字、巨大な展開データ
- ファジング: ランダムなバイト列をデコーダに入れても、落ちずに拒否か正常な結果だけを返す
- 量子化: パレットの色だけで描いた画像は誤差0で、正しいパレットが自動で選ばれる
- QR: 生成したQR行列を別実装のデコーダで読み、URLが一致する。密度の高い最悪ケースも含める
- 画面(Playwright): 受信URLを開く → プレビュー → 保存 → 再読み込みでも残る → URLの `#` が消える

**実機テスト(手動)**

- 端末: iPhoneとAndroid(PixelやGalaxyなど)を、標準カメラで少なくとも各機種を2つずつ
- 条件: 明るい屋外、画面の明るさが低い、斜めから、手ぶれ、距離(20〜50cm)
- 確認: 最悪ケースと実例のQRが1秒以内に読める距離、`$ * +` を含むURLが欠けずに開けるか、iOSのSafariとホーム画面アプリの保存先、AndroidでのPWAリンク挙動、オフライン起動

## マイルストーン

最大の不確実性は「屋外でQRを読み取れるか」と「iOSで保存が残るか」なので、作成UIより先に受け渡しを実機で通す(M2)。各マイルストーンは、該当する節と完了条件だけで実装を任せられる粒度にしている。規模は相対的な目安で、日数は見積もっていない。

| マイルストーン | 内容 | 完了条件 | 規模 |
| --- | --- | --- | --- |
| M0 仕様の確定 | パレット32種の色とID、SNS4種の許可文字とURLの確認、縁取りの太さ、ペイロードのテストベクタ | 未決事項のうちM0分が決まり、テストベクタがリポジトリに入る | S |
| M1 コア | payload、palette、render、sns、qr(43文字方式)と、そのテスト。UIはなし | 往復・ベクタ・拒否・ファジング・QR復号のテストがCIで通る | M |
| M2 受け渡しの縦スライス | 固定のサンプルを表示 → QR → 別端末の標準カメラ → 受信画面 → 保存。PWAとオフラインも含む | iPhoneとAndroidで、明るい屋外を含めて読める。密度の警告しきい値を決め、iOSの保存先とAndroidのPWAリンクの挙動を確認する | M |
| M3 作成(画像インポート) | 画像選択、クロップ、縮小、手動パレット選択、透明設定、SNS入力、自分のステッカーの保存 | 写真とドット絵の両方を取り込んで、交換まで通せる | L |
| M4 パレット自動選択と固定モード | 自動選択、パレットの書き出し(PNG、.gpl)、完全一致した画像の自動判定 | 外部ツールでパレット通りに描いた32×32が誤差0で取り込まれる | S |
| M5 シール帳 | コレクション一覧、ページ、配置操作、保存、バックアップ(書き出し・読み込み)、永続化の要求 | 実機で数百枚を滑らかに操作でき、バックアップから復元できる | L |
| M6 印刷 | SVG出力、カットライン、A4割り付け、サイズ指定 | 実際の用紙に試し刷りして、サイズと色を確かめる | M |
| M7 仕上げ | 色以外の手がかりやタップ領域、文言、エラー表示、ホーム画面追加の案内、IDの扱いの注意書き | 公開できる状態 | M |

M4はM3の後、M5と並行して進められる。M6はM5と、ステッカーの描画(core/render)を共有するだけなので、M1が終わればいつでも着手できる。

## リスクと未決事項

最も重いリスクは、屋外でQRを読めないことと、iOSで保存が見えない・消えること。どちらもM2の実機テストで早い段階に確かめる。

| リスク | 起きること | 対策 |
| --- | --- | --- |
| 屋外でQRが読めない | 交換できない | 密度の警告、誤り訂正M、43文字方式、全画面表示。M2で実測してしきい値を決める |
| 受け取る人の電波が弱く、初回にページを開けない | 初回の受信が失敗する | Service Worker、事前に開いてもらう案内。初回だけは完全には防げない |
| iOSでSafariとホーム画面アプリの保存先が別、未追加のデータは消えうる | 集めたステッカーが見えない、あるいは消える | リンクのコピーと貼り付け取り込み、ホーム画面追加の案内、バックアップ。挙動は実機で確認する |
| 標準カメラの挙動差(長いURLや記号) | URLが欠ける、開けない | M2の実機確認。開けない場合のフォールバックとして「リンクをコピー」を用意する |
| なりすまし、不適切な画像 | 他人のIDを載せたステッカー、不快な絵を受け取る | なりすましは検証できないので対応しない(決定)。不適切な画像は、受信時のプレビューと破棄で各自が判断する。リンクはテンプレートで組み立てる。画像の自動検出は対象外 |
| IDが見える範囲に出る | QRを写真に撮った周囲の人にもIDが渡る | 作成時に注意を表示し、QRは交換するときだけ全画面で出す。サーバーがないので有効期限は付けられない |
| パレットの色が印刷で変わる | 期待と違う色になる | 試し刷りと注意書き |
